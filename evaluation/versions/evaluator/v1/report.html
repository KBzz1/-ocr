第 一 章为什么是评估

一切始于一个直白的问题：怎么证明改 prompt 是变好了，而不是碰运气？项目的最大需求是准确性——病历字段抽取错一个数值，医生就要多花一分钟核验。但翻开代码，找到的却是这样一个 harness：

prompt 组装 → complete_json → 契约校验 → evidence 回填 → quality_flags → 人工审核页

链路干净，验证层（契约校验、薄规则、医生兜底）已成型。唯独缺少一件事：没有一把尺子。没有评估集、没有指标、没有基线——每一次 prompt 改动都是凭感觉，而"凭感觉"恰恰是准确性项目最昂贵的习惯。

对照《深入理解 AI Agent》的评估方法论（第六章），这个判断变得明确：

「没有评估，就没有进步。」评估对象不是模型，而是「模型 + harness 的组合体」——分数下降时，问题可能不在模型，而在 harness。 ——《深入理解 AI Agent》引言 / 第六章
HARNESS（马具） — harness
LLM 之外的全部工程层：上下文、工具、约束、验证、纠正。生产系统中重心在后三者——"能做事"的部分要薄，"不做错事"的部分要厚。

1.1 一开始以为该做的是别的事

最初的两个候选是上下文工程和多 Agent 协作——它们是书里最引人注目的两章。但逐条对照项目现状后，两个都排除了：单次调用场景下，上下文管理已踩在正确范式上（固定字段表静态 + evidence 动态追加）；多 Agent 协作的判据是"协作是否引入单 Agent 无法获得的新信息"，而本项目的单次抽取 + 人工审核已经用上了唯一合理的形态。

金标 GOLDEN SET — golden set
带标准答案的测试样本。评估时把抽取结果与金标逐字段比对，算出指标。金标质量决定评估可信度——宁少勿滥。

把"准确性"这个词工程化，落点只有一个：评估。而项目恰好拥有一份别处拿不到的黄金资源——医生审核修正后的字段结果，天然就是金标标注。

第 二 章设计：三个关键决策

2.1 决策一：评估先行，不做上下文工程、不做多 Agent

三条路线（评估先行 / 验证器先行 / 文档先行）摆在面前。选定评估先行：先有尺子，再谈改进——验证器改动有没有效，也要靠评估来度量。这个顺序避免了"改进无法度量"的死循环。

实验 0-1 ★ 金标语义的裁定

问题：OCR 把"无"丢了（"呼吸困难"变阳性），金标该判什么？

裁定：金标 = 「从这份 OCR 输入出发，期望抽取输出什么」。OCR 错读是 OCR 层的问题，不属于 agent 观测——agent 忠实摘录 OCR 阳性表述就是正确的。三个 agent 语义层裁定：乙肝否定算 found（保留否定词）；"血糖异常"未明说糖尿病 → uncertain；血气在现病史段仍算 found（抽取应不依赖文档顺序，OCR 拼接错序时模型要发挥泛化性）。

2.2 决策二：五个确定性指标，不用 LLM 打分

指标判定方式性质
status 准确率found/not_found/uncertain 严格比对完全确定性
value 准确率归一化一致 / 互为子串 / 人工裁定确定性两级
幻觉数（veto）value 必须在 OCR 原文可定位一票否决
任务级成功率61 字段全对仅参考（样本少方差大）
契约非法率payload 校验失败比例确定性
否决项 VETO — veto dimension
幻觉不是扣分项，是归零项。这与项目硬约束「不得补造字段，宁可 not_found」完全同构——书里叫"幻觉一票否决"，项目里叫"宁缺毋滥"。

2.3 决策三：最窄边界，审核回流留到下一步

医生审核数据回流（金标活资产）是明确的价值点，但第一步刻意不做——6 份人工金标先把体系立起来，回流机制等验证器规范化时一并设计。边界划清，scope 才能守住。

3.1 过程中的工程决策

  • worktree + data 符号链接：金标提炼要读主工作区的 data/text_data，worktree 是分支副本不含数据——符号链接解决，数据不进 git，两不相扰。
  • 消融开关只立接口：诚实评估过——当前管线层不改 value，消融对比收益有限；但"消融开关必须从第一天设计进架构"（书里原话），接口先立，等复核器接入后才有用武之地。
  • LLM 失败兜底：真实 QwenVLLMClient 服务不可用时抛 RuntimeError，会穿透整个评估循环——样本级兜底 + 失败详情落报告，评估永不因单样本中断。
实验 1-1 ★ 计划缺陷的现场修复

实施中发现 3 处计划（brief）自身缺陷，实施者现场最小修正：相对导入路径错误（...errors → ..errors）；消融模式下契约复验会抛异常（改为 error=None + 空 candidates）；幻觉错误明细与自带测试断言冲突（收敛为"纯 veto 个案才进明细"）。三处均经独立审查判定合理。

第 四 章首个基线：尺子量出了什么

评估报告  Qwen3.5-4B-AWQ-4bit / admission_record_structured_fields_prompt.v1
──────────────────────────────────────────────
样本数        : 6   (噪声带宽 ±0.2041)
status 准确率 : 98.09%
value 准确率  : 88.32%
幻觉数(veto)  : 43
契约非法数    : 0

最差字段 top5 : hpi_treatment_medications 0/6 · pe_nose 0/6
                hpi_hospital_diagnosis 3/6 · hpi_subsequent_course 4/6 …

数字本身是次要的——这把尺子第一次让"哪里差"变成了可回答的问题。逐条核查错误明细后，三个改进方向浮出水面：

实验 4-1 ★★ 幻觉判定误报：否定短语重建

金标 value「否认糖尿病病史」在 OCR 原文（否认"糖尿病"、"冠心病"等病史）同样不可定位——这类规范化重建是 prompt 契约明确要求的输出，幻觉判定对它系统性误报（24/43 条幻觉为此类）。

修正方向：金标 value 本身不可定位的字段，应跳过幻觉判定（契约要求的重建 ≠ 编造）。

实验 4-2 ★★ J 型字段与长文本字段的判定粒度

pe_nose 金标 value「正常」，抽取输出「鼻腔通畅」——语义等价，字面互不为子串，被判 mismatch（0/6）。hpi_treatment_medications 这类长摘录字段同理：摘录范围差异导致判定过严。

修正方向：J 型字段的 value 判定放宽为语义等价；长文本字段改用关键词覆盖或人工裁定。

这三个观察，正是"评估让改进有依据"的最好注脚——不是模型不行，是指标本身需要进化。它们已记入工作记录，成为第二步验证器规范化的输入。

第 五 章复盘：什么做对了

5.1 做对的事

  • 先定语义再定指标："金标 = 从 OCR 输入出发的期望输出"（agent 观测）这一裁定，避免了整套评估建在错误的观测对象上；
  • 确定性优先：有金标就比对，不引入 LLM 打分——无长度偏差、无同源模型盲区、零额外成本；
  • 审查 gate 全程有效：6 个任务 × 独立审查，计划缺陷（导入路径、消融语义、断言冲突）在合入前被拦下，最终审查仅 1 条 Important（已修复）；
  • 基线是一次性投入：之后每次改 prompt、换模型，一条命令出对比——回归机制让 prompt 从"契约变更"升级为"可度量变更"。
