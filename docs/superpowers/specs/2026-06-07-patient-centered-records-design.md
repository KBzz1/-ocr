# 患者中心记录归档设计

## 背景

当前系统以任务为核心：一次任务包含一批图片、一轮 OCR/结构化处理、一份人工审核结果和对应导出。任务之间没有患者归属关系，因此同一患者在不同时间形成的多次记录无法集中阅览。

本功能在不改变现有处理链路的前提下，引入轻量患者档案和记录时间，使用户能够：

- 创建任务前明确患者和记录归属；
- 在患者维度查看不同记录类型及其历次结构化结果；
- 保持每次任务结果独立，不自动合并不同时点的信息。

本设计描述首版可用范围，不将当前交互和字段约束写成永久不可扩展限制。

## 术语

### 患者

系统内用于归集多个任务的轻量档案。首版仅要求：

- 系统生成的患者编号；
- 必填患者姓名；
- 创建时间、更新时间；
- 逻辑删除状态。

患者姓名用于展示和搜索，不作为唯一标识，也不与 OCR 内容自动比对。

### 记录类型

替代用户界面中的“文书类型”称谓，例如“入院记录”。后端和 API 继续使用现有 `document_type` / `document_type_label` 作为唯一数据源，不新增同义的 `record_type` 字段，避免双字段不一致。

### 记录时间

用户在创建任务时填写的病历记录发生时间：

- 记录日期必填；
- 具体时分可选；
- 不使用任务创建时间冒充记录时间。

### 患者中心

以患者档案为入口，按记录类型和记录时间组织其关联任务。结构化字段仍归属于具体任务，不形成跨任务“患者总字段”。

## 目标

1. 一个患者可以关联多个任务。
2. 同一患者、同一种记录类型可以存在不同时间的多次记录。
3. 一个任务只对应一位患者的一份记录，可包含多页图片。
4. 用户可在患者详情页集中阅览历次结构化结果。
5. 现有上传、处理、审核、重抽取和导出主链路保持可用。
6. 首版保持简单，不引入复杂患者主索引或医院系统集成。

## 非目标

首版不实现：

- HIS/EMR 接口或医院患者主索引同步；
- 根据 OCR 姓名自动匹配或校验患者；
- 跨任务自动合并结构化字段；
- 自动判断不同档案是否为同一患者；
- 患者合并界面；
- 回收站和用户恢复界面；
- 完整操作历史查看界面；
- 患者别名、身份证号、性别、年龄、住院号、病案号等扩展身份字段；
- 多用户权限、审批或协作流程。

患者合并、恢复和更丰富的身份字段可作为后续能力，但不阻塞首版交付。

## 产品流程

### 新建任务

用户点击“新建任务”后，系统先展示一个统一弹窗，所有归属信息在同一表单中填写，不拆成向导步骤：

1. 选择已有患者，或在弹窗内新建患者；
2. 选择记录类型；
3. 填写记录日期；
4. 可选填写具体时间；
5. 提交后创建 `uploading` 任务；
6. 创建成功后展示手机上传二维码。

创建任务前必须完成患者、记录类型和记录日期填写。具体时间允许为空。

新建患者时若存在同名患者，系统先展示同名档案及患者编号、任务数、最近记录时间。用户确认后仍可创建同名患者，系统不得自动复用或禁止创建。

首版由前端在提交前执行精确姓名查询并展示确认提示；患者创建 API 本身允许重名，不引入重复患者事务或锁定协议。

### 上传与处理

手机端仍只负责向当前任务上传多张图片并完成上传。二维码已经绑定任务，因此手机端不再填写患者或记录信息。

现有手机上传页中的记录类型选择入口随本功能移除。记录类型只能在电脑端创建任务时选择，避免扫码后改变已经确认的任务归属。

现有状态保持不变：

```text
uploading -> processing -> review -> done
                       \-> failed
```

患者姓名不参与 OCR、结构化抽取或任务成败判断。

### 患者阅览

电脑端主导航新增“患者管理”，与“任务管理”并存：

- 患者管理负责患者搜索、建档和长期归档阅览；
- 任务管理继续负责处理状态、失败排查和任务级操作。

患者详情页采用：

- 左侧：记录类型导航及该类型的记录数量；
- 右侧：当前记录类型的任务时间轴，默认按记录时间倒序；
- 每条记录显示记录时间、任务编号和任务状态；
- `review` / `done` 记录可展开只读结构化字段摘要；
- `uploading` / `processing` / `failed` 记录只显示状态和可执行操作，不展示尚不存在或不可读的结构化字段；
- 字段摘要按当前 Schema 分组展示全部字段，包括空字段；
- `review` / `done` 记录提供“进入审核/查看结果”入口，复用现有审核页完成图片、OCR 和字段核验。

所有状态的未删除任务都出现在患者详情页，包括 `uploading`、`processing`、`review`、`done` 和 `failed`。

## 数据模型

### Patient

建议首版属性：

```json
{
  "patient_id": "P-A1B2C3D4",
  "name": "测试用例",
  "created_at": "2026-06-07T10:00:00+08:00",
  "updated_at": "2026-06-07T10:00:00+08:00",
  "deleted_at": null,
  "name_history": []
}
```

约束：

- `patient_id` 由系统生成且不可变；
- 编号格式不作为业务语义；实现使用 `P-` 加 UUID4 的前 8 位大写十六进制字符，生成后检查是否已存在，碰撞时重新生成；不依赖现有患者数量，不复用已删除编号；
- `name` 必填，允许重名；
- 修改姓名后，患者页、任务页和后续导出使用当前姓名；
- 每次改名向 `name_history` 追加修改前姓名、修改后姓名和修改时间；首版不提供历史查看界面。

### Task 扩展

现有任务增加：

```json
{
  "patient_id": "P-A1B2C3D4",
  "document_type": "copd_admission_record",
  "document_type_label": "入院记录",
  "record_date": "2026-06-07",
  "record_time": "09:30",
  "deleted_at": null,
  "patient_snapshot": {
    "patient_id": "P-A1B2C3D4",
    "name": "测试用例"
  }
}
```

说明：

- `document_type` / `document_type_label` 沿用现有字段和算法配置；仅用户界面统一展示“记录类型”；
- `record_date` 必填；
- `record_time` 可空；
- 日期使用 `YYYY-MM-DD`，时间使用本地时间 `HH:mm`，按工作站时区解释，不做 UTC 换算；
- 先按记录日期倒序；同一天内有具体时间的记录按时间倒序排列，仅填写日期的记录排在当天有具体时间的记录之后；
- `patient_snapshot` 在任务创建、改绑时写入；患者被逻辑删除时，用删除前当前姓名刷新其关联任务快照；
- `patient_snapshot` 用于患者被删除后继续识别任务原归属，不作为患者正常存在时的姓名来源；
- 正常情况下患者当前姓名是界面和导出的权威值。

### 归属变更记录

`uploading` 阶段允许直接修改患者、记录类型和记录时间。

任务处于活跃 `processing` 时，不允许修改患者、记录类型或记录时间，避免后台处理使用的任务快照与持久化元数据不一致。用户需等待处理结束，或先取消处理。

任务进入 `review`、`done` 或 `failed` 后仍允许更正，系统记录：

- 修改字段；
- 修改前值；
- 修改后值；
- 修改时间。

首版不要求用户填写修改原因，也不提供完整历史查看页面。
变更记录只保存上述必要字段，不在首版扩展为通用审计系统。

患者和记录时间属于归档元数据，更正后不改变 OCR、字段候选或审核结果。

记录类型决定 Schema 和抽取配置，处理后更正记录类型时不得只改标签：

1. 用户确认后更新 `document_type` 及其版本元数据；
2. 复用现有任务图片重新进入完整 `processing`；
3. 新处理结果回到 `review`；
4. 不继续展示或导出旧记录类型下的审核字段；
5. 重新处理失败时任务进入 `failed`，遵循现有失败契约。

## 页面设计

### 患者管理

主要能力：

- 按患者姓名或患者编号搜索；
- 新建患者；
- 查看患者详情；
- 修改患者姓名；
- 逻辑删除患者。

列表至少展示：

- 患者姓名；
- 患者编号；
- 关联的未删除任务数量；
- 最近记录时间。

默认不显示已逻辑删除患者。

### 新建任务弹窗

同一弹窗并列展示：

- 患者选择器，支持搜索已有患者；
- “新建患者”轻量入口；
- 记录类型选择器；
- 记录日期；
- 可选具体时间；
- “创建任务”按钮。

表单校验通过并创建任务后，弹窗内容切换为二维码和任务摘要，不在提交前展示二维码。

### 患者详情

患者头部展示：

- 当前患者姓名；
- 患者编号；
- 修改姓名；
- 新建该患者任务；
- 逻辑删除患者。

内容区采用“记录类型导航 + 类型内时间轴”。同类记录不合并字段；`review` / `done` 记录展开后展示该任务的完整只读字段摘要。

字段摘要采用按需加载：仅在用户展开 `review` / `done` 记录时复用该任务现有审核结果接口，不在患者详情接口中复制一份结构化字段契约。

### 任务管理与审核页

任务管理增加：

- 患者姓名和患者编号；
- 记录类型；
- 记录时间；
- 患者已删除标记；
- 改绑患者入口。

审核页保留现有职责，并在页头显示患者姓名、患者编号、记录类型和记录时间；不在患者详情页直接编辑结构化字段。

## 任务改绑

任务可改绑到：

- 一个现有患者；
- 操作过程中创建的新患者。

创建任务和改绑只允许选择未删除患者。若患者在用户提交前已被删除，后端拒绝操作并返回患者不可用错误，前端刷新患者列表后要求重新选择。

改绑后：

- 任务出现在新患者详情页；
- 原患者详情页不再显示该任务；
- 后台记录原患者、新患者和变更时间；
- OCR、结构化字段、审核结果和导出记录不变。

## 删除规则

所有删除均为逻辑删除，首版不物理删除患者、任务、图片、OCR 结果、审核结果或导出记录。

现有任务删除 API 当前会物理删除任务 JSON 并调用清理服务删除关联目录。实施本功能时必须改为逻辑删除，正常删除路径不得再调用 `CleanupService.cleanup_task`。物理清理只允许作为独立维护能力存在，不暴露在首版用户界面。

删除患者时提供两个选择：

### 仅删除患者

- 患者默认不再出现在患者管理中；
- 关联任务继续显示在任务管理中；
- 任务标记“患者已删除”；
- 任务保留患者编号和姓名快照；
- 用户可将任务改绑到现有患者或现场新建患者。

### 同时删除患者和关联任务

- 若存在 `processing` 任务，拒绝该操作并提示用户先取消或等待处理完成；
- 患者和关联任务都标记为逻辑删除；
- 这些任务从任务管理和患者详情默认隐藏；
- 后台完整保留原始记录和关联关系；
- 首版不提供恢复入口。

逻辑删除任务后，普通任务列表、详情、审核、重抽取和导出接口均将其视为不可用；只有内部维护代码可显式读取已删除记录。

对普通 API，已逻辑删除任务沿用 `TASK_NOT_FOUND`，避免引入一套可被用户操作的“已删除任务状态”。患者不存在使用新增 `PATIENT_NOT_FOUND`；患者已删除或不可绑定使用新增 `PATIENT_DELETED`。新增错误码需先写入共享错误码文档。

患者合并后迁移全部任务的规则属于后续能力，不纳入首版界面和接口验收。

## 导出

单任务 JSON、Excel 以及批量 JSON zip 中的单任务导出模型增加：

- 患者编号；
- 患者当前姓名；
- 记录类型；
- 记录日期；
- 可选具体时间；
- 任务编号。

导出继续使用该任务人工审核后的最终结构化字段，不改变字段 Schema、字段状态或证据语义。

患者姓名修改后，再次导出使用当前姓名。后台可保留旧姓名审计记录，但首版导出不包含姓名历史。

患者已删除但任务被保留时，导出使用任务中的删除前患者姓名快照，并明确标记患者已删除。已逻辑删除任务不可导出。

## API 能力边界

实施阶段预计增加或扩展以下能力，具体路径由实施计划结合现有路由风格确定：

- 创建、查询、搜索、修改和逻辑删除患者；
- 查询患者详情及关联任务；
- 创建任务时提交患者、记录类型和记录时间；
- 修改任务归属元数据；
- 改绑任务患者；
- 删除患者时选择是否同时逻辑删除关联任务；
- 任务列表和详情返回患者与记录元数据；
- 导出模型返回患者与记录元数据。

现有任务状态枚举、上传令牌、处理端口、审核字段契约和错误处理原则保持不变。

所有患者相关日志只记录 `patient_id`、`task_id`、状态和错误码，不记录患者姓名、OCR 原文或字段值。

## 与现有文档的差异

本设计批准后，实施阶段需要同步修订以下现行契约：

- `docs/PRD文档/产品PRD.md` 当前规定点击“新建任务”立即创建任务并展示二维码；新行为改为先在统一弹窗填写归属信息，提交后才创建任务和展示二维码。
- 当前核心实体没有 `Patient`，任务也没有记录时间；需补充 PRD 数据实体和接口概要。
- 当前界面使用“文书类型”相关表述；用户界面统一改为“记录类型”，底层继续使用 `document_type`，不新增同义字段。
- 当前手机上传页允许修改 `document_type`；新流程在电脑端创建任务前确定记录类型，因此手机端该入口需移除。
- 当前任务删除会物理删除任务并清理关联文件；新行为必须改为逻辑删除，正常用户删除不得调用清理服务。
- `docs/Shared/terminology.md` 需增加患者、患者编号、记录类型、记录时间和患者中心定义。
- 前后端 BDD/TDD 和 `docs/PRD文档/PRD任务清单.md` 需按实施任务同步更新。

本设计不修改任务状态枚举。实施需要新增 `PATIENT_NOT_FOUND` 和 `PATIENT_DELETED`，并在编码前写入 `docs/Shared/error-codes.md`；其他参数错误优先复用 `INVALID_REQUEST_PARAMS`，状态冲突优先复用 `INVALID_TASK_TRANSITION`。

## 测试数据整理

当前仓库仍处于测试阶段。实施该功能时执行一次性开发数据整理：

- 删除或逻辑删除现有测试任务，仅保留一个可见测试任务；
- 创建一个姓名为“测试用例”的患者；
- 将保留任务绑定到该患者；
- 为该任务补充一个有效记录类型和记录日期；
- 不在业务代码中写死该患者或任务；
- 整理动作通过一次性脚本、fixture 或明确的开发数据步骤完成。

该要求只针对当前开发环境，不构成生产数据迁移策略。

- 删除患者的两个选项产生正确可见性；
- 已删除患者关联的保留任务显示明确状态。

## 验收标准

1. 用户可新建患者，或在新建任务弹窗中选择已有患者。
2. 用户在同一弹窗填写患者、记录类型、记录日期和可选时间，提交后才获得二维码。
3. 同一患者可创建多次同类型记录，患者详情按记录时间稳定排序。
4. 患者详情中的 `review` / `done` 记录可展开全部结构化字段，并进入审核页；其他状态只展示状态和可执行操作。
5. 患者姓名修改后，关联任务展示和再次导出使用当前姓名。
6. 任务可以改绑患者，已有图片、OCR、字段和审核结果不丢失。
7. 删除患者不会物理删除数据；保留任务可识别原患者已删除并支持改绑。
8. 导出包含患者编号、当前姓名、记录类型、记录时间和任务编号。
9. 现有上传、处理、审核、重抽取和导出主流程回归通过。
10. 开发环境最终只保留一个可见测试任务，并绑定“测试用例”患者，且没有业务代码写死测试数据。
11. 处理完成后更正记录类型会重新处理，不会把旧 Schema 字段冒充为新记录类型结果。
12. 用户删除任务或患者时不会触发任务文件、图片或结果文件的物理清理。

## 实施拆分

本功能使用一个总 spec，但实施计划拆成三个可独立验收的任务。

### 任务 1：患者实体与任务绑定

- 契约文档和测试设计；
- 患者存储、编号、创建、搜索和改名；
- 任务增加患者与记录时间元数据；
- 创建任务、查询任务和改绑接口；
- 后端单元测试与 API 契约测试。

验收结果：后端能够稳定创建患者，并创建或改绑带患者归属的任务。

### 任务 2：患者中心页面与新建流程

- 统一新建任务弹窗；
- 患者管理列表和搜索；
- 患者详情的记录类型导航、时间轴和字段摘要；
- 任务管理和审核页补充患者与记录信息；
- 前端组件测试和关键流程测试。

验收结果：用户可完成“建档/选患者—创建任务—患者详情阅览—进入审核”的完整闭环。

### 任务 3：逻辑删除、导出与测试数据整理

- 患者删除的两个选项；
- 已删除患者任务标记和任务默认可见性；
- 导出患者与记录元数据；
- 一次性测试数据整理；
- 前后端回归测试及 PRD/BDD/TDD/任务清单收口。

验收结果：删除不造成数据物理丢失，导出元数据完整，开发环境测试数据符合约定。
