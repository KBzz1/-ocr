01背景与动机

本项目是离线病历文书结构化采集与人工核验工作站，COPD 入院记录抽取核心位于 app/backend/services/copd_extraction/。当前管线形态为单次 LLM 调用：

prompt 组装 → complete_json → 契约校验 → evidence 回填 → quality_flags → 人工审核页

对照《AI Agent 实战营》教材第 6 章评估方法论，现状的关键缺口：

  • 没有任何正确率度量 —— 每次改 prompt 都是凭感觉，无法回答「这次改动真的变好了吗」；
  • 本书核心公式「Agent = LLM + 上下文 + 工具」中，本项目无工具调用、无多 agent、无记忆需求，评估正是「准确性」的工程化度量；
  • 已有黄金资源：医生审核修正后的字段结果、人工标注数据 data/text_data/（6 份干净病历 + 对应 OCR 结果）→ 可直接提炼为字段级金标。
📖 书上原话：「没有评估，就没有进步」—— 评估对象不是模型，而是「模型 + harness 的组合体」。

02目标与边界

目标

建立「评估 = 金标比对 + 字段级指标 + 回归基线」的最小闭环：

  1. 一套字段级金标评估集（6 份起步，可扩展）；
  2. 五个确定性指标（不依赖 LLM 打分）；
  3. 可重复执行的评估脚本，支持模型替换实验与消融变体参数；
  4. 基线快照 + prompt 回归对比机制。

边界（明确不做）

不做什么时候做
审核数据自动回流第二步「验证器规范化」
复核器接入活动路径第二步
抽取轨迹日志落盘第三步
LLM-as-a-Judge 评分器有金标，确定性比对优先，不做
多 agent / 记忆 / 上下文压缩 / 工具安全本项目场景不需要

03评估集（golden set）

位置

  • 金标目录：data/evaluation/golden/case_001.json ~ case_006.json
  • 报告目录：data/evaluation/reports/
  • 不进 gitdata/ 已在 .gitignore / .git/info/exclude 排除，金标为运行数据

样本格式

{
  "case_id": "case_001",
  "ocr_text": "<ocr_results/1.txt 原文>",
  "pitfalls": ["negation", "ocr_typo"],
  "golden": [
    {"field_key": "chief_complaint", "status": "found", "value": "反复咳嗽、咳痰20年，喘累2年，加重10余天"},
    {"field_key": "pmh_diabetes", "status": "found", "value": "否认糖尿病病史"}
  ]
}
  • status 只允许 found / not_found / uncertain，与抽取契约一致；
  • golden 必须覆盖 schema 全部 61 字段，未提及的字段为 not_found + 空 value。

金标生成流程

  1. 从 data/text_data/ground_truth/*.txt 干净病历文本提炼 61 字段初稿（提炼脚本放 scripts/ 下，一次性使用）；
  2. 同时生成每份病历的 OCR 差异清单（ground_truth 与 ocr_results 的文本差异，供快速定位错读处）；
  3. 用户（医生视角）复核初稿，重点裁定 OCR 错读处的预期输出（保留原文 / uncertain / ocr_correction）；
  4. 裁定结果回写金标，以裁定为准修正金标 value。

质量控制（宁少勿滥）

6 份起步；每份标注 pitfalls 陷阱类别，指标报告按类别分组诊断：

negationocr_typonumeric_conflictdiagnosis_numberingblood_gas_shared_evidenceaux_missing

04指标设计

核心原则：能用确定性比对就不用 LLM 打分。61 个字段按判定策略分三类。

指标 1：status 判定准确率 完全确定性

found / not_found / uncertain 与金标一一比对，按字段、按陷阱类别分组统计。

  • 金标 found 而抽取 not_found = 漏抽（召回损失）
  • 金标 not_found 而抽取 found = 多抽（幻觉风险）

指标 2：value 正确率 归一化两级判定

判定规则结果
归一化一致去空白、全半角、标点后完全一致✅ 正确
互为子串归一化后预测值是金标的子串（或反之），截断摘录视为合理✅ 正确
都不满足疑似错误，进错误明细⚠️ 人工裁定，裁定结果回写金标
  • 金标 not_found 时不做 value 比对（预测 value 必须为空串，非空即错）；
  • uncertain 的 value 不做严格比对，仅计入 status 指标。

指标 3：幻觉率（veto 维度，不需要金标就能判）

value 必须在 ocr_text 中可定位（归一化子串查找）。value 中出现 OCR 原文没有的内容 = 幻觉/补造，直接违反项目硬约束「不得补造字段」。

例外：该字段 ocr_correction 非空时，以修正链判定 —— 修正后的 value 与 OCR 原文 + 修正理由一致则不记幻觉（OCR 错读纠偏是受控行为，非补造）。

🚫 书里的「幻觉一票否决」：幻觉不是扣分项，是归零项 —— 与本项目「宁可 not_found 也不编造」完全同构。

指标 4：任务级成功率 仅参考

61 字段 status 全对 + value 全对 = 成功。样本 6 份时方差极大，报告标注噪声带宽，不作为主线指标。

指标 5：契约非法率

validate_qwen_payload 失败比例（任务进 failed 的源头之一）。

统计显著性

报告标注样本量与噪声带宽（√(p(1-p)/n)）；指标 diff 小于带宽不视为改进。主线盯字段级指标而非任务级。

05评估执行

命令形态

python -m app.backend.evaluation.run_eval \
  --golden data/evaluation/golden \
  --model <模型名> \
  [--no-quality-flags] [--no-contract]
  • 复用 COPDAdmissionQwenFieldPort，注入真实 vLLM 客户端；
  • 每条样本跑完整管线（prompt 构建 → LLM → 契约校验 → evidence 回填 → quality_flags），收集 payload / candidates，与金标比对；
  • 评估脚本不引入业务代码侵入，与 pytest 单测（注入 fake client）互不干扰。

模型替换实验

--model 切参同命令跑两遍，报告直接可比 —— 这就是 ch6 归因实验的最小形态：固定 harness 只换模型。

消融开关（第一步只立接口）

诚实声明：当前活动管线这些层不改 value（质控只加标记、契约只拦失败），现有消融对比收益有限；接口先立是「消融开关必须从第一天设计进架构」的要求，真正用武之地是第二步复核器接入后的「有复核 vs 无复核」对比。

06报告与回归机制

报告输出

  • 控制台汇总：总表（5 指标）+ 按字段分组表 + 按陷阱类别分组表；
  • JSON 落盘 data/evaluation/reports/<日期>_<prompt版本>_<模型>.json，含逐字段错误明细；
  • 报告头部记录：prompt 版本、模型名、schema 版本、参数、样本数。

回归流程（写进工作方式）

首次跑通 → 存为基线 baseline_<prompt版本>.json
修改 prompts.py → 跑评估 → 对比基线（指标 diff + 字段错误明细 diff）→ 有收益才合入

diff 小于噪声带宽不视为改进。

08测试约定

  • 指标比对逻辑（归一化、子串判定、幻觉定位、分组统计）需要有 pytest 单测，注入合成数据，不依赖真实 LLM；
  • 评估脚本本身用手写 fixture 冒烟（不需要真实推理即可验证脚本链路），真实推理跑 data/evaluation/golden/。
