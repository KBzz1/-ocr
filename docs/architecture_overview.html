编排核心：ProcessingOrchestrator

三段式管道

顺序执行 图像处理 → 文档解析 → 字段抽取，任一阶段端口未配置或契约非法都会让任务进入 failed。

  • 每个阶段都会调用 _is_cancelled 检查用户是否取消。
  • 阶段进入 gpu_stage_queue，保证 GPU 同一时刻只跑一段。
  • 失败时记录 error_code + stage + reason。

错误码 & 边界

  • ALGORITHM_MODULE_NOT_CONFIGURED — 端口未注入。
  • ALGORITHM_MODULE_FAILED — 外部模块异常。
  • ALGORITHM_CONTRACT_INVALID — 返回结构非法。
  • REVIEW_VALIDATION_FAILED — 字段候选缺失。
  • 所有错误码统一在 docs/Shared/error-codes.md 维护。

🚫 后端边界（hard rule）

  • 不接入医院 HIS/EMR，不写回病历系统，不生成诊断结论或医学建议。
  • 不依赖云 API、CDN、遥测；不进行运行时联网下载模型。
  • 不在本仓库实现 OCR、图像处理、裁剪、透视矫正——这些由外部本地算法模块提供。
  • 本仓库只编排"慢阻肺/呼吸系统入院记录"的字段抽取，不扩展为通用医学规则引擎。
03

OCR 识别 · PaddleOCR-VL on vLLM Server

采用 Vision-Language 多模态模型 PaddleOCR-VL，常驻为 vLLM HTTP 服务，从而避免每次冷启动加载模型带来的几十秒延迟。

🔍

架构形态

  • 常驻 vLLM Server 监听 :8080/v1。
  • 主进程通过 PaddleOCRVL(vl_rec_backend="vllm-server", vl_rec_server_url=...) 远程调用。
  • 每张图调用 pipeline.predict(input=path, max_new_tokens=1024, max_pixels=501760)。
  • 超时由 ThreadPoolExecutor + future.result(timeout=240s) 强制守护。

输入 / 输出契约

输入：

{
  "task_id": "t_2026...",
  "pages": [
    {"page_id":..., "page_no":1,
     "processed_path":"./data/.../p1.jpg"}
  ]
}

输出（关键字段）：

{
  "pages": [{"page_id", "text", "status"}],
  "merged_text": "主诉：...\n现病史：..."
}

GPU 调度策略

  • OCR 与 LLM 共用一张卡，由 GpuStageQueue 串行化两个阶段。
  • 避免 OCR vLLM Worker 与 llama-cpp GPU layer 同时申请显存。
  • 事件日志记录 ocr_vlm_started / ocr_vlm_finished + 耗时 + 字节数。
  • vLLM Server 失败时主进程不退出，任务标记为 failed 由人工重试。
流式输出处理

结果解码

PaddleOCR-VL 直接输出 Markdown，主进程优先读 result.markdown；若为空则调用 save_to_markdown(temp_dir) 落盘临时文件再读回，最后按页拼接成 merged_text。

def _extract_markdown(result_item):
    md = getattr(result_item, "markdown", "")
    if md.strip(): return md.strip()
    # Fallback：临时目录读 .md 文件
    with TemporaryDirectory() as d:
        result_item.save_to_markdown(save_path=d)
        ...

失败语义

  • 输入图片缺失 → RuntimeError("OCR 输入图片不存在")。
  • 单页 markdown 为空 → 该页 status="failed"，error_message 显式写入。
  • 任一页失败 → has_failure=True，整任务进入 failed。
  • 超时 → concurrent.futures.TimeoutError 包装为 RuntimeError，事件日志写 exit_code=-1。
04

LLM 结构化抽取 · 双 LLM 流水线

同一个 Qwen2.5-7B 本地模型，承担两种截然不同的人格：先做"抽取者"，再做"审核者"。这是项目最有意思的一段。

🧠

共享基座：LlamaCppClient

抽取 LLM 与审核 LLM 都通过同一个 LlamaCppClient 调用 llama-cpp-python 本地推理，参数：

model: qwen2.5-7b-instruct-q4_k_m (GGUF) n_ctx: 8192 n_gpu_layers: -1（全 offload） temperature: 0.0 response_format: json_object

  • JSON-only 输出：模型直接走 JSON mode；返回还做了一次防御性 _extract_first_json_object，能从 ```json ... ``` 围栏、尾部多余逗号等容错恢复。
  • 截断检测：finish_reason == "length" 立即抛 ValueError，防止半截 JSON 被静默吃掉。
  • 显存释放：每个 LLM 任务跑完调用 close() + gc.collect()，配合 GpuStageQueue 让 OCR / LLM 可以交替使用同一张卡。
1

section_splitter

用正则切出 8 个标准章节，含别名映射（"查体"→"体格检查"）。

2

抽取 LLM

按章节分组发 prompt，强约束 evidence_phrase ≤50 字。

3

把 source_hint 反查回章节原文，丢弃越界 evidence。

4

本地薄规则：数值不在 evidence、生理范围、零体重下降…

4.1 抽取 LLM · Extractor 人格
🤖

抽取 LLM

"你是慢阻肺/呼吸系统入院记录结构化抽取引擎。只从 OCR 原文中抽取字段，不得推断原文未写的信息。"

两种抽取策略（通过 extraction_strategy 切换）：
  • field_batches（默认 batch=25）：把所有字段按批次塞给 LLM，每批输出一个 JSON。
  • section_groups（推荐）：先把 OCR 按 8 个章节切片，再把字段按"病史档案 / 体格检查 / 辅助检查"三组合并发送，显著减少 prompt 长度和幻觉。
SECTION_GROUPS 分组：

history_profile physical_exam auxiliary_exam

OCR 风险提示（写进 system prompt）： 
# 字形混淆
1/I/l, 0/O/o, BHI/BMI, cT/CT/Ct
# 血气项目名错读
P62/P02/PC02 → PO2/PaO2/PCO2/PaCO2
# 药名近形/同音
嗜托溴铵 → 噻托溴铵
二程丙苯碱 → 二羟丙茶碱
# 单位/符号
+10^9/L 可能是 ×10^9/L
硬约束（写进 prompt）：
  • 不得静默修正 OCR — 必须输出 ocr_correction.applied / raw / normalized / reason。
  • 不得改写数值；不得医学换算。
  • 不得把"无、否认、未见、可能、考虑、建议复查"改成确定阳性。
  • evidence_phrase ≤ 50 字 且必须是 OCR 原文片段。
输出契约： 
{
  "fields": [{
    "field_key": "temperature",
    "original_value": "36.7℃",
    "source_hint": "体格检查",
    "evidence_phrase": "体温：36.7℃",
    "confidence": 0.9,
    "ocr_correction": {
      "applied": false,
      "raw": "",
      "normalized": "",
      "reason": ""
    }
  }]
}
"source_hint 重生成"二次纠偏：

如果 LLM 把 source_hint 输出成了内部分组名（history_profile）或编造章节，后端会自动发起 SourceHintRegenerationStrategy，让 LLM 仅在合法章节白名单中重选。

🛡️

4.2 审核 LLM · Verifier 人格

"你是字段级复核器。只能根据 OCR 事实判断，不得使用医学常识补全，不得修改字段值，不得把否定或不确定表述改成确定阳性。"

输入：source_groups（按章节聚合的字段集合）

同章节字段一起发给审核 LLM，让它看到完整上下文（章节原文 + 文档背景），而不是单字段孤立判断。

必填 checks 五件套：

source_text_supported ocr_correction_reasonable numeric_value_preserved negation_preserved section_assignment_reasonable

verdict 三档：

pass · 完全可信  suspicious · 需人工核验  fail · 明显有错

reason_code 枚举： 
original_text_ambiguous   # 原文歧义
low_ocr_quality            # OCR 错读
extraction_error           # 抽取错误
unreliable_result          # 结果不可信
source_section_not_found   # 来源章节不存在
none                       # 通过
典型审核规则（写进 prompt）：
  • 血气项目名出现 P62/P02/PC02 但被归入 PO2/PaCO2，缺少 ocr_correction 即 suspicious + reason_code=low_ocr_quality。
  • 同段出现"脉搏：9 次/分"和"心率 99 次/分"→ 禁止静默选值 → suspicious。
  • "体重减轻 0g/0kg" → 明显矛盾 → suspicious，提示人工核对。
  • verdict=fail 时回写 quality_flags = ["llm_review_failed"]。
合并阶段：_merge_verdicts 
if verdict == "pass" and not item["quality_flags"]:
    item["verification_status"] = "passed"
elif verdict == "fail":
    item["verification_status"] = "failed"
    _append_flag("llm_review_failed", ...)
elif verdict == "suspicious":
    item["verification_status"] = "suspicious"
    _append_flag("llm_review_suspicious", ...)
4.3 抽取 LLM ↔ 审核 LLM 之间的"薄规则"层

quality_checks · 不替代 LLM、不修字段

纯本地 Python 规则，只输出 quality_flags 警告，不会让任务失败、也不会改字段值。它是一道"廉价的低成本预筛"，常常能在 LLM 之前就提前标红。

  • value_not_in_evidence 数值在 value 但不在 evidence。
  • suspicious_date 出现未来年份。
  • negation_or_uncertainty_risk evidence 含"无/否认/未见/可能"。
  • possible_duplicate_or_stitching 全文高相似句重复。
  • ocr_label_ambiguity 血气标签疑似错读。
  • unit_symbol_ambiguity +10^9/L vs ×10^9/L。
  • ocr_numeric_conflict 脉搏:9 vs 心率99 矛盾。
  • counterintuitive_zero_weight_loss 体重下降 0kg。
  • physiologic_range_risk 体温 <32 或 >43、脉搏 <20 或 >240、pH <6.9 或 >7.8。
  • blood_gas_label_not_whitelisted 血气标签不在白名单。

evidence 智能恢复

当 LLM 给出的 evidence 超过 50 字 / 不在 source_text 中 / 完全缺失时，后端不会扔掉字段，而是用 _recover_evidence_from_value 在章节文本中查找 original_value 周围 ±N 字的最小窗口作为 evidence，并把字段标记为 suspicious，最终把决定权交给人工审核。

if raw_evidence_too_long:
    _flag("evidence_too_long")
if raw_evidence_not_in_source:
    _flag("evidence_not_in_source_text")

recovered = _recover_evidence_from_value(
    item.original_value, source_text, max_chars=50)
if recovered:
    item["evidence"] = recovered
    item["verification_status"] = "suspicious"

5.1 证据高亮 · 一键定位 OCR 原文

实现路径

审核页右侧选中字段 → 取该字段的 evidence → 在合并后的 OCR 文本里 indexOf 命中位置 → 用 <mark> 包裹 → scrollIntoView({ block:'center' }) 自动滚动到中心。

  • ≤100 字才高亮：超过则提示"片段过长，不进行高亮，请人工核验"。
  • 支持 stripOcrMarkup 去除 OCR 自带的 HTML/&nbsp;。
  • 精确匹配失败 → 按行 / 标点 / 引号拆分候选，挑最早出现且最长者。

视觉演示

主诉：反复咳嗽、咳痰 8 年，加重伴喘息 3 天。
体格检查：体温：36.7℃，脉搏 88 次/分，呼吸 22 次/分。
辅助检查：动脉血气：pH 7.36，PaO2 62 mmHg，PaCO2 48 mmHg。
诊断：慢性阻塞性肺疾病急性加重期。

↑ 选中 temperature 字段时，高亮自动落在体温片段上。

5.2 审核功能 · 字段级状态机

字段状态

每个字段独立的小状态机：

unreviewed confirmed modified

  • auto_value 是 LLM 抽取的初值，永远保留。
  • final_value 是人工最终落定值。
  • 修改一次写一条 history，可回溯。
  • empty_accepted 允许医生显式确认"字段确实空"。

批量信号汇总

审核页顶部 review summary：

  • total_count / confirmed_count。
  • verification_status 分布：passed / suspicious / failed。
  • quality_flags 计数（薄规则告警数）。
  • 所有字段 confirmed 之后才能 complete → done。

重新打开 reopen

任务已 done 但医生发现问题：

  • 调用 POST /api/review/{id}/reopen。
  • 状态从 done 回退到 review。
  • 历史 history 与 auto_value 不变。
  • 导出文件不会被删除，只是不再代表最新版本。
5.3 文书模板 · DocumentProfile 体系

什么是 DocumentProfile

本仓库当前只服务一种文书 —— COPD 入院记录。但代码已经把"文书模板"做成了一等公民：

DocumentProfile(
  document_type="copd_admission_record",
  label="入院记录",
  schema=schema_service.get_current(),
  prompt_version="copd_extraction_prompt.v1",
  field_port=copd_field_port,
  quality_rule_profile="copd_admission_record")

未来新增文书（如出院小结、手术记录），只需要注册一个新的 Profile，不需要改 Orchestrator、不需要改前端。

Schema 驱动一切

  • app/config/schemas/copd_admission_record.v1.yaml 是字段契约的源头。
  • 字段分组、字段顺序、标签、字段类型全部从 schema 读取。
  • 前端 FieldList 直接按 field_groups 渲染分组。
  • SchemaValidator 在抽取阶段尾巴对 final_value 强制类型校验。
  • schema_version 写进 review_result、export，保证未来升版可识别。
5.4 其它产品级小心思

重抽取（基于已存 OCR）

OCR 阶段非常贵（vLLM Server），所以 ReextractionService 只重跑 字段抽取，跳过图像处理 + 文档解析，直接读 document_result.json 重新喂给 LLM。改 prompt、调参后秒级反馈。

批量导出 · JSON / Excel / Zip

支持单任务导出 JSON 或 Excel；批量场景生成 zip：包含所有任务的 JSON + 一个汇总 Excel。每次导出会在 exports/ 产生稳定文件名，便于追踪。

离线巡检 OfflineCheckService

启动时检查：模型文件是否存在、vLLM Server 是否可联、磁盘空间、Schema 是否可解析。前端在工作台顶部展示一条 "系统提醒" 横幅，把问题暴露给医生。

手机扫码 · 同局域网

_get_lan_addresses 通过 UDP connect 嗅探出站 IP（不发包、不依赖 DNS），生成多个候选地址 → 二维码 → 手机扫码进入采集页。"手机连不上？"弹窗给出诊断提示。

GPU 阶段队列

用一个全局 GpuStageQueue 让 document_parsing 与 field_extraction 不会同时抢卡。同时事件日志会记录每段的开始/结束时间，方便事后排查显存抖动。

启动遗留任务清理

CleanupService 在后端启动时扫描所有 processing 任务（说明上次进程被强杀），按业务约定标记为 failed，避免任务"永远卡在处理中"。

5.5 可观测性 · 双日志体系

LocalEventLog · 热日志

滚动 JSONL 格式，记录所有业务事件：task_created / ocr_vlm_started / extraction_finished / system_started / review_saved……每条带 level、timestamp、payload，便于回放问题。

boot.log / debug.log / access.log · 冷日志

主进程 stdout/stderr 全部重定向到 boot.log，避免污染热日志；Werkzeug access log 落到 access.log；调试细节落到 debug.log。三份冷日志按大小滚动，最多保留 N 份，不上传任何远端。
