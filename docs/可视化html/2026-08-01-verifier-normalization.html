第 1 章为什么做这件事

第一步评估体系跑出首个基线，数据摆在面前：

指标基线暴露的问题
status 准确率98.09%7 处 status 误判
value 准确率88.32%34 处 value 误判——部分是判定逻辑冤枉了模型
幻觉数（veto）4324 处是"否定短语重建"误报——金标本身在原文不可定位
任务级成功0/66 份样本全未达标，样本量小方差大，不作主线

三个结构性问题浮出水面：

1
复核器是死代码。prompts 里躺着两个写好的复核器 prompt（设计意图是让 LLM 再查一遍抽取结果），但从未接入活动路径——而审核链路（quality_flags → suspicious → 审核页）是活的。
2
指标有误报。幻觉判定冤枉"否定短语重建"；J 型字段"正常"vs"鼻腔通畅"语义等价被判错；长文本摘录范围差异判定过严。
3
审核数据没有回流。医生在审核页的修正值只留在本地 JSON 里，没有变成可复用的金标资产——最珍贵的学习信号在流失。
评估体系的最大价值不是一次性度量，而是让每一次 prompt / 模型变更都有度量支撑； 第二步让"复核器"这个评估出来的薄弱环节真正转起来，并让医生修正反哺评估。

第 2 章目标与边界

2.1 六个目标

1
复核器接入活动路径：抽取 → 复核 → 可疑字段进审核页，可消融对比（--no-verifier）
2
验证器校准：kappa ≥ 0.7 才上岗
3
审核数据回流：医生修正 → 脱敏 → 金标活资产（source: review，与 manual 分开统计）
4
指标修正：幻觉豁免 / J 型语义归一 / 长文本核心句重合
5
消息结构适配 Qwen ChatML：system（规则）+ user（数据）分层
6
thinking 消融开关（--thinking），用评估体系实测 CoT 收益——不拍脑袋

2.2 明确不做

不做为什么
分歧触发定向重抽取复核意见只做标记，不做二次抽取——最窄边界，复用现有通道
复核意见原文展示给医生LLM 复核文本不进前端（防误导），前端沿用规则化提示
抽取轨迹日志落盘第三步的事
换模型 / 换温度制造复核独立性本地单一 Qwen 模型、温度恒 0.0——可复现是校准的前提
复核 not_found 字段漏抽由审核页兜底

第 3 章复核器设计

3.1 位置与形态

新模块 copd_extraction/verifier.py，FieldVerifier 类。输入抽取结果 + 原文 + schema + LLM 客户端，输出按字段 verdict。复核范围：status=found 且 value 非空 的字段。

抽取
→
薄规则 quality_checks
→
LLM 复核器
→
合并 flags
→
分歧字段 → suspicious → 审核页

verdict=suspicious/fail → 新增 quality_flags（verifier_suspicious + reason_code）→ verification_status=suspicious → attention_required=True，前端展示固定纯中文提示"复核器标记，请核对原文"。

接入挂点 wiring points
生产路径 port.extract 增加可注入 verifier；评估路径 run_pipeline 增加 apply_verify 开关；run_eval --no-verifier 做"有复核 vs 无复核"对比——与第一步消融架构完全同构。

3.2 Prompt 结构：ChatML 分层 + 防锚定布局

system（完全固定，前缀缓存友好）：身份（字段级复核器）· 缺陷清单（否定翻转 / OCR 标签混淆 / 数值矛盾 / 纠偏合理性 / 生理范围）· verdict 契约（pass/suspicious/fail + reason_code + checks + comment ≤40 字 + 必须引用 evidence 编号）· 对抗精神（先找茬，找不到才 pass）· few-shot（pass / suspicious 各一个结构示例）

user（变量区）：evidence 在前（原文证据，带编号）→ 字段在后（field_key + 声称的 value + 引用的 evidence_ids）

为什么 evidence 在前、字段在后 anti-anchoring
字段值在前会让复核器顺着值找证据支持（找补 / 确认偏误）；evidence 在前，模型先读原文事实、形成自己的判断，再看到"声称的值"——找补的路被堵死。同时 evidence 先出场引导注意力，第一遍 pass 就是扫原文。

3.3 同源模型缓解

抽取与复核是同一 Qwen 模型、同一温度 0.0。系统性偏差无法消除，缓解全在上下文：

手段机制
evidence 前置防锚定：先看原文再看到抽取值
缺陷清单把已知易错点（否定翻转、OCR 标签、数值矛盾…）写进指令，告诉模型"去这里找"
引用 evidence 编号可疑 verdict 必须拿原文说话，而不是顺着抽取值
verdict 型主干 + 对抗精神可校准（kappa）+ 有锐度（先找茬再放行）

3.4 Thinking 消融（--thinking）

实验 3-1 ★ CoT 收益实测

开 thinking（CoT）可能提升抽取/复核质量，但有三怕：thinking 挤占 61 字段 JSON 的输出预算（截断 → 契约非法）、json_object 与 thinking 的兼容性未验证（固定 digest 镜像）、响应变长（医生等待敏感）。

不拍脑袋：--thinking 消融开关，同一批金标跑两轮实测对比指标 + 契约非法数 + 时长。默认值：抽取先保守 off，复核倾向 on（verdict 输出小、推理任务收益大）——由实测数字决定。

第 4 章消息结构改造：适配 Qwen ChatML

现状问题：complete_json 把整个 prompt（身份+硬约束+字段表+原文）塞进一条 user 消息——Qwen 训练时 system / user / assistant 是三种有区分度的角色，官方最佳实践是角色规则放 system、实际数据放 user。讽刺的是 OCR 路径（complete_text_from_image）已是 system+user 双消息，抽取路径反而没有。

改造前改造后
system—（无）身份 + 硬约束 + 固定字段表 + 输出契约 + 再次强调
user整个 prompt 字符串evidence_units + OCR 原文（变量数据）

complete_json 签名扩展支持 system+user 分离，不传 system 时行为不变（向后兼容）。system 完全固定 → 前缀缓存命中率最大化（固定前缀变长）。

第 5 章验证器校准：kappa ≥ 0.7 才上岗

Cohen's kappa 一致度系数
衡量复核器判定与人工裁定的一致性（扣除随机一致）。≥ 0.7 视为合格。单位是字段级：人工对每条 verdict 裁定"该字段是否应被标记可疑"——与字段金标不同维度（金标裁值对错，校准集裁可疑性）。

校准流程：

6 份金标样本跑真实抽取+复核
→
约 180 条字段级 verdict
→
导出人工裁定模板
→
人工逐条裁定
→
kappa ≥ 0.7？
→
达标 → 接入活动路径

工具：evaluation/calibrate.py（跑复核 → 导出裁定模板 → 算 kappa）。不达标就迭代 prompt（缺陷清单 / few-shot / 布局）重测，不达标不接入。校准集存 data/evaluation/calibration/（运行数据，不进 git）。

第 6 章审核数据回流：金标活资产

审核确认（complete_review）
→
聚合 auto_value ≠ final_value 字段
→
回流文件（运行数据）
→
脱敏
→
金标活资产 source: review

6.1 采集

字段结构天然支持回流：auto_value 恒为抽取原值、final_value 为医生最终值，二者不等即"修正过"。确认时聚合写入 data/evaluation/review_feedback/<task_id>.json（含患者信息，不进 git）。status 规则：修正值非空记 found，修正值为空串（医生清空误值）记 not_found——"医生认为该字段不存在"本身是金标信号。

6.2 脱敏

轻量正则：手机号 / 身份证 / 住院号 / 11 位数字串；日期保留（病历日期是抽取语义的一部分）。回流原始文件不脱敏，脱敏发生在生成金标活资产时。

6.3 金标活资产

增量修正字段文件（不要求 61 字段全量），data/evaluation/golden_review/<task_id>.json，source: "review"。评估工具按 source 子集单独统计"修正字段错误率"——修正字段 = 抽取器易错字段，盯住它们就是盯住实际伤害。

为什么只回流修正字段 signal not noise
医生确认的字段与抽取一致，不携带新信息；修正字段才是学习信号。全量回流只会把数据放大 4-5 倍、全是噪音。

第 7 章指标修正：三个冤枉好人的判定

误报场景实例修正机制
幻觉误报
否定短语重建不可定位		 原文"否认'糖尿病'、'冠心病'等病史"，抽取按契约输出"否认糖尿病病史"——原文找不到这句话 → 判幻觉 先测金标 value 可定位性：金标不可定位 → 该字段跳过幻觉判定（期望输出本身就是重建短语）。真错误由 value_mismatch 兜底
J 型粒度误判
"正常" vs "鼻腔通畅"		 pe_nose：金标"鼻腔通畅"、抽取"正常"，语义等价被判 mismatch 从 schema 加载 J 型字段清单（qwen_type=J / review_control=judgement），仅这些字段做"正常族"归一：正常/通畅/未见异常/无异常/阴性/无压痛 → 同一 token
长文本摘录过严
摘录范围差异		 金标摘 A 段、抽取摘 B 段，内容都对，被判错（hpi_* 现病史类） 长文本字段（初始：hpi_* 类 + chief_complaint）改判核心句重合率：按句切分后共有句占比 ≥ 0.6 判对
重要：口径影响

三处修正都改变 value_accuracy 统计口径——修正后基线必须重跑。报告 meta 记录指标版本号，对比时显式标注。

第 8 章评估执行与消融矩阵

python -m app.backend.evaluation.run_eval \
  --golden data/evaluation/golden \
  --schema app/config/schemas/admission_record_structured_fields.v1.yaml \
  --model <模型名> \
  [--no-verifier] [--no-quality-flags] [--no-contract] [--thinking]
开关含义
--no-quality-flags跳过薄规则 quality_checks（第一步已有）
--no-contract跳过契约校验（第一步已有）
--no-verifier跳过复核器（本步新增）
--thinking开启 Qwen thinking 模式（本步新增）

典型对比：--no-verifier vs 默认（复核器对质量指标的影响）；--thinking vs 默认（CoT 收益与代价）。
