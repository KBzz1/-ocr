第 一 章为什么是复核器

1.1 复核器一直是死代码

第一步的复盘里留了一句话：审核链路（quality_flags → verification_status=suspicious → attention_required → 审核页）是活的，但产生这些标记的复核器（build_verification_prompt / build_adversarial_verification_prompt）从设计之初就没有被任何调用方使用。第二步要做的不是发明新东西，而是把设计意图真正接进管线——并回答一个更尖锐的问题：它值得上岗吗？

上岗门槛 KAPPA ≥ 0.7 — go-live gate

复核器与人工裁定的一致性用 Cohen's kappa 度量；kappa ≥ 0.7 才允许接入活动路径（生产与评估共用同一 verifier 实现）。这条门槛写在设计文档里，本步用真实样本验证了它——结论是暂不上岗。

1.2 本步的五件事

① 复核器接入评估管线（可消融：--no-verifier）；② 校准：kappa ≥ 0.7 后上岗；③ 医生审核数据回流为金标活资产（source: review）；④ 修正三个指标误报；⑤ prompt 适配 Qwen ChatML 分层 + thinking 消融实测。

第 二 章设计：关键决策

2.1 同源缓解：不引入第二个模型

复核器与被复核的抽取器是同一个 Qwen 模型、温度恒 0.0——同源模型做对抗复核，只能靠上下文差异缓解锚定：evidence 前置在后（复核器先读证据再看法定值，防"找补"）、缺陷清单逐项核对、suspicious/fail 的 verdict 必须引用具体证据编号（eXXX）。

2.2 失败静默降级是铁律

复核器 LLM 调用失败 / 输出非 JSON / verdict 契约非法 → 空意见 + 记日志，绝不抛出、绝不导致任务失败、绝不修改字段值。这条铁律在 thinking 实测中被真实触发过一次（非 JSON 输出），降级机制按设计工作——复核器可以不存在，但不能制造故障。

2.3 ChatML 分层：system 固定、user 变量

vLLM 已开启 --enable-prefix-caching，prompt 拆成 system（身份、硬约束、字段表、契约——完全固定）与 user（证据单元、OCR 原文——变量数据），固定部分全命中前缀缓存。拆层由测试锁死：system 中不得出现任何证据/原文变量。

2.4 指标修正：三个误报源

第一步基线暴露的误报：① 金标 value 本身不可定位（否定短语重建，如"否认糖尿病病史"）被当幻觉——金标不可定位时跳过该字段幻觉判定；② J 型字段"鼻腔通畅"与"正常"被当成不同值——正常族归一（正常/通畅/未见异常/阴性…→统一 token）；③ 长文本字段（hpi_*、chief_complaint）精确比较过于苛刻——核心句重合率 ≥ 0.6。

3.2 计划文本的现场修复

实施中发现的三处计划内部矛盾，均以"测试意图优先"裁定：system 模板示例 evidence id（u001）与新测试断言互斥；回流金标键名（fields vs golden）以评估消费契约 golden 为准；句子重合率逐字实现的数值（1/3）与断言（≥0.5）矛盾——改为对称包含判定。这类偏差在每轮评审中独立复核，未引入契约漂移。

实验 3-1 ★ J 型归一的接线缺口

评审发现：生产 schema（v1）61 个字段完全没有 qwen_type / review_control 注解——J 型归一是死代码，生产审核路径的 J 型推断同样是死代码（既有隐藏问题）。用户裁决"仅评估路径合并 v2 注解"（最窄边界）：run_eval 从批处理 schema 合并 18 个同名 J 字段注解，不碰生产契约。

第 四 章四轮运行：数字说了什么

4.1 修正后基线：幻觉 43 → 13

实验 4-1 ★★★ 指标修正前后对比

status 98.09% → 98.36%（+0.27）　value 88.32% → 89.35%（+1.03）　幻觉 43 → 13（−30）　契约非法 0 → 0　任务级 0/6 → 0/6

幻觉 −30 是三个指标修正的直接收益：否定短语重建的期望输出不再被计为幻觉（约 30 个字段从"模型幻觉"翻案为"判定误报"）。value +1.03% 来自 J 型归一的评估路径接线（鼻腔通畅 == 正常）。任务级 0/6 是既有状态：任务级判定要求全字段成功，本步未修改该口径。

4.2 消融对比：复核器对指标零影响（设计使然）

--no-verifier 与默认运行的指标完全一致（98.36 / 89.35 / 13）。这不是巧合而是铁律的结果：复核器不修改字段值，只追加 quality_flags 与 suspicious 标记——评估指标不读这些信号。复核器的影响面在审核页（可疑字段进人工核验），不在指标。这也意味着"复核器让指标变好/变坏"不是它的评价方式，一致性（kappa）才是。

4.3 校准：kappa 0.40 → 0.45，未达上岗线

实验 4-2 ★★★ 校准执行与结论

48 条 verdict（suspicious 29 / fail 1 / pass 18）→ 36 个去重字段由 Claude 子 agent 模拟医生逐条裁定（8 应标 / 28 不应标）→ 官方 kappa = 0.3962（表 [[18,0],[16,14]]：无漏报，但 flagged 30 条中 16 条误报）。

迭代 1（证据一致性硬约束 + 找茬失败转 pass + 误报反例）：官方 kappa 0.4545，但同键公平口径持平（0.4615 → 0.4444）——官方提升是键集漂移的假象（export 重跑抽取非确定性）。

根因：4B 模型复核存在能力天花板——编造指控（声称值"删了偏字"但值里就有）、套用缺陷模板未核对值、医学常识错误（"经口吸入应为经皮吸入"）。降误报与防漏报是跷跷板：保守化后出现"值退化为纯标签仍 pass"的漏报苗头。

结论（用户裁决：接受现状收尾）：复核器 kappa 不达标，活动路径保持不注入（spec 5.2 上岗门槛被尊重）；评估路径可消融使用；校准/回流/指标基础设施完整保留，待模型升级后重校准。

4.4 thinking 消融：无收益，默认关闭

--thinking 开启后 status 98.09%（−0.27）、value 87.97%（−1.38）、幻觉 13 持平，且出现 1 次复核器输出非 JSON（静默降级机制按设计工作）。结论：4B 模型 CoT 在抽取任务上无收益甚至略降，默认保持关闭，开关保留供模型升级后复测。

第 五 章复盘：做对的与留到下一步的

5.1 做对的事

指标修正把噪声清掉了。幻觉 43 → 13 说明第一步的"尺子"本身有 30 个误报——先校准尺子再量产品，是评估体系该有的顺序。静默降级被真实触发且可靠。复核器失败、非 JSON 输出都没能扰动任何任务。ChatML 分层与消融开关就位。前缀缓存、thinking、verifier 三个开关都可以独立对比。数据闭环基础设施完整。回流（脱敏 → 金标活资产）、校准（裁定模板 → kappa）都是真实可用的工具链，第一步"审核回流留到下一步"的承诺兑现。

5.2 留到下一步的事

复核器上岗需要更强的模型。编造指控是 4B 模型的能力问题而非 prompt 缺失——prompt 工程把 kappa 从 0.40 推到 0.45 已近极限，建议模型升级后复用现有校准工具链重测（缺陷清单补"值退化"型、export 复用抽取结果 + verdict 去重消除键集漂移）。活动路径复核器暂不注入。kappa 不达标期间审核页继续由既有薄规则（quality_flags）兜底。--golden-review 统计局限。回流金标不含 OCR 原文，修正字段错误率衡量的是"空文档命中"——未来在回流文件补存 ocr_text（本就不进 git，PII 面不变）即可让该指标真正可读。任务级 0/6 是既有口径问题，留给第三步。
